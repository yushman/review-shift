# review-shift

**review-shift ночью ревьюит локальные git-ветки и к утру кладёт на стол отчёт и готовый
к применению git-патч, вместо ревью, которое откладывается до момента после мержа.**

[English version](README.md)

> **Статус: выпущен v0.1.3.** `pipx install review-shift` ставит его из PyPI.

---

## Что он делает

Ночью, без человека рядом, `review-shift`:

1. находит локальные ветки, которые недавно двигались (`refs/heads/`, по committer date);
2. строит дифф каждой ветки против точки ветвления с базовой веткой;
3. маскирует значения секретов до того, как что-либо уйдёт модели;
4. прогоняет read-only код-ревью заданной глубины;
5. пишет markdown-отчёт, `findings.json` и два файла патчей, причём каждый патч перед
   записью на диск проверяется через `git apply --check`.

Утром вы читаете один файл и применяете один патч. `review-shift` ничего не применяет сам,
не коммитит, не пушит и не трогает рабочее дерево.

## Требования

- macOS для запуска по расписанию (`launchd`), машина на питании от сети и не спит: см.
  «Ограничения». Сам CLI работает на Linux и macOS, x86 и ARM.
- CLI [Claude Code](https://claude.com/claude-code) **версии 2.1.0 или новее**, уже
  залогиненный.
- Python 3.11+.

## Установка

```bash
pipx install review-shift
```

## Основной сценарий

```bash
# подготовить репозиторий: создаётся .review-shift/config.yml,
# артефакты прогонов исключаются из git
cd ~/proj/myrepo && review-shift init

# проверить окружение, прежде чем доверять ему ночь
review-shift doctor

# поставить ночной прогон (генерируется launchd-джоба, регистрируется пробуждение)
review-shift init launchd
```

Утром:

```bash
$EDITOR .review-shift/runs/latest/report.md
```

## Настройка конфига

`review-shift init` создаёт `.review-shift/config.yml` с комментариями прямо в файле: это и
есть справочник. Несколько полей, с которыми стоит познакомиться до первой тонкой настройки:

| Поле | По умолчанию | |
|---|---|---|
| `depth` | `medium` | `smoke` \| `low` \| `medium`: задаёт пресет промпта, effort и лимита находок; лестница — ниже |
| `scope.full_file_review` | `auto` | `auto` \| `always` \| `never`: перекрывает дефолтный scope глубины; `never` опускает его до изменённых hunk-ов, `always` поднимает до изменённых файлов целиком, `auto` следует depth. Что это контролирует на `medium` — см. «Ограничения» |
| `discovery.patterns` | `[]` | fnmatch-глобы (или regex через `re:`), ограничивающие список веток; пусто = «любая недавно двигавшаяся ветка» |
| `discovery.max_age_hours` | `24` | ветка попадает в выборку, только если последний коммит внутри этого окна |
| `runtime.budget_usd` | `10.00` | лимит трат на ревью одной ветки |
| `runtime.total_budget_usd` | `50.00` | лимит трат на весь прогон; по исчерпании оставшиеся ветки помечаются `skipped: budget_exhausted`, это не ошибка |
| `runtime.auth_preflight_budget_usd` | `0.01` | бюджет дешёвой проверки здоровья окружения, которую `run`/`doctor` делают перед тем, как тронуть хоть одну ветку; поднимите значение, если она падает с «exhausted its own budget»: на машине с тяжёлым глобальным конфигом (много MCP-серверов/плагинов) даже самый первый вызов дороже копейки |
| `patch.auto_fix_min_severity` | `high` | минимальная severity, которая попадает в `auto_fixed.patch`, а не только в `all.patch` |
| `trunk.enabled` | `false` | вместо discovery веток ревьюит коммиты, попавшие прямо на базовую ветку — см. «Ревью trunk» ниже |
| `trunk.max_commits_per_run` | `10` | лимит коммитов за один trunk-прогон; остаток забирается следующей ночью |

### Глубина

| `depth` | что читает модель | effort | ≈ на ветку |
|---|---|---|---|
| `smoke` | только изменённые hunk-и | `low` | ~$0.38, ~1 мин |
| `low` | изменённые файлы целиком | `medium` | ~$0.52, ~2 мин |
| `medium` | изменённые файлы плюс их прямые импорты первого уровня | `high` | ~$0.77, ~3.5 мин |

Новые установки по умолчанию идут на `medium`. Ночной прогон никто не ждёт, поэтому три с
половиной минуты на ветку не стоят ничего для спящего пользователя, а траты в любом случае
ограничены предохранителем `runtime.total_budget_usd`. Опуститесь до `low`, если ветки за ночь
считаются десятками, или до `smoke` для быстрой прикидки — `smoke` видит только hunk-и, чего
хватает заметить локальную ошибку и не хватает оценить, насколько она важна.

Цифры ориентировочные, сняты на маленьком корпусе бенчмарка; это не заявление о качестве
(см. «Ограничения»).

> **`high` больше не существует.** До v0.1.3 лестница была `low | medium | high`; каждый
> уровень сохранил своё поведение и сдвинулся на одно имя вниз (`low`→`smoke`,
> `medium`→`low`, `high`→`medium`), а `high` убран, а не сделан алиасом — слот зарезервирован
> под действительно более глубокий уровень. `--depth high` теперь падает и сообщает, что
> писать вместо него. Конфиг править не нужно: файл с `version: 2` мигрируется в памяти при
> загрузке по той же таблице, а на диске остаётся нетронутым. Первый прогон после обновления
> переревьюит все ветки, потому что файлы промптов изменились.

Любое скалярное поле `runtime`/`discovery`/`patch` (а также `depth`/`base_branch`) можно задать
и через переменную окружения `REVIEW_SHIFT__<SECTION>__<FIELD>` (например,
`REVIEW_SHIFT__RUNTIME__AUTH_PREFLIGHT_BUDGET_USD=0.10`). Приоритет: файл конфига →
env-переменная → CLI-флаг, там где флаг есть: `run --depth`/`--model` и ещё несколько
перебивают оба.

## Предпросмотр ночи (`--dry-run`)

```bash
review-shift run --dry-run
```

прогоняет discovery, собирает диф каждой ветки от merge-base, применяет редактирование
секретов, пишет каталог прогона с отчётом — и **не делает ни одного вызова модели**, включая
preflight-проверку авторизации, так что стоит это ноль. В отчёте перечислена каждая ветка,
которую бы отревьюили, база, с которой её сравнивали, глубина, которая бы применилась, и
размер каждого дифа.

Это отвечает на то, что `doctor` не проверяет: `doctor` доказывает, что окружение здорово, но
никогда — что discovery выбрал ожидаемые ветки, что диф собирается от резолвленной базы и что
отчёт рендерится. Dry-run берёт тот же лок, что и настоящий прогон, никогда не двигает
указатель `latest` и никогда не может быть отдан как кэш-хит следующему настоящему прогону —
пользуйтесь свободно, в том числе вместе с `--trunk`.

## Ревью trunk (`--trunk`)

Discovery веток намеренно пропускает базовую ветку — её ревью отвечает на другой вопрос: «что
попало прямо в `main` с прошлого раза», а не «что изменилось относительно точки ветвления,
которой у `main` самой по себе нет». `review-shift run --branch main`, когда `main` —
резолвленная базовая ветка, теперь ошибка использования, указывающая на `--trunk`, а не тихий
пустой прогон.

```bash
review-shift run --trunk
```

ревьюит коммиты, попавшие прямо на резолвленную базовую ветку (`git rev-list --reverse
--first-parent --no-merges`, от старых к новым), по одному, слитые в один отчёт и одну пару
патчей против текущего head базовой ветки. Коммиты, пришедшие через смерженную feature-ветку,
никогда не выбираются — эта работа уже прошла через discovery веток, — так что ничего не
оплачивается дважды.

Прогресс отслеживается персистентным watermark (`index.json`), а не временным окном, поэтому
пропущенная или запоздавшая ночь никогда не ревьюит коммит повторно и не пропускает его молча.
**Первый прогон после включения `trunk.enabled` (или флага `--trunk`) не ревьюит ничего** — он
инициализирует watermark на текущий head и начинает ревью со следующего прогона; это осознанно,
причина `bootstrap` указана в Summary отчёта. Коммит, содержимое которого полностью заменено
более поздним, пропускается как `superseded` до всякого вызова модели; слишком большой для
ревью коммит пропускается громко, как coverage gap, а не заклинивает все последующие прогоны.

Каждая находка trunk называет свой коммит и автора, и указывает, доступен ли ещё `amend`/rebase
(коммит ещё локальный) или остаётся только fix-forward (коммит уже запушен).

Включить через конфиг вместо флага:

```yaml
trunk:
  enabled: true
  max_commits_per_run: 10
```

## Демо

```bash
asciinema play demo/review-shift.cast
```

Находки в записи это сценарий ради быстрого, бесплатного и воспроизводимого прогона: `init` и
артефакты патча/отчёта в записи настоящие, произведены тем же кодом (`patch.resolve` /
`patch.generate_and_verify` / `report.render`), что и реальный ночной прогон. Запись
пропускает живой вызов модели, который делает `review-shift run`, а `doctor` в записи не
запускается вовсе, потому что его проверка авторизации тоже живой вызов.

## In-session ревью (`/review-shift`)

`review-shift` также работает изнутри сессии Claude Code как скилл, который вызывает тот же
CLI (ADR-006): те же промпты, тот же лок, тот же отчёт. Ограничение: одна ветка и
`depth <= low` — интерактивная сессия не место для самого долгого и широко читающего ревью:
`medium` запускайте через `review-shift run`. Два способа получить его, не взаимоисключающие:

```bash
# без зависимости от маркетплейса, точная команда `/review-shift`, без авто-обновления
review-shift init skill
```

```
# внутри сессии Claude Code: self-hosted маркетплейс, авто-обновление, namespaced-команда
/plugin marketplace add https://github.com/yushman/review-shift
/plugin install review-shift@review-shift
# вызывается как /review-shift:review-shift (Claude Code всегда добавляет плагину префикс)
```

`init skill` пишет `.claude/skills/review-shift/SKILL.md` в текущем репозитории; перезапустите
её после обновления `review-shift`, чтобы подхватить изменившийся скилл. Канал плагина
подхватывает изменившийся скилл командой `claude plugin update review-shift@review-shift`. Оба
канала можно поставить одновременно: Claude Code держит рядом и исходный `/skill-name`, и
копию плагина.

## Как применить патч

Осознанно вручную и осознанно в три шага. Патч привязан к вершине ветки на момент прогона.

```bash
# 1. sha, против которого собран патч, указан в заголовке патча и в run.json
git -C . rev-parse feature/payments-v2

# 2. проверить применимость
git switch feature/payments-v2
git apply --check .review-shift/runs/latest/patches/auto_fixed.patch

# 3. применить
git apply .review-shift/runs/latest/patches/auto_fixed.patch
```

Если ветка ушла вперёд от этого sha, CLI печатает объяснение вместо рецепта, а не делает
вид, что патч всё ещё применим.

## Что появляется на диске

```
.review-shift/
├── config.yml                  # предназначен для коммита
└── runs/
    ├── 2026-08-22T03-30-00Z-feature-payments-v2/
    │   ├── report.md           # то, что читаете утром
    │   ├── findings.json
    │   ├── run.json            # ветка, sha, глубина, стоимость, тайминги, счётчики
    │   ├── events.jsonl
    │   └── patches/
    │       ├── auto_fixed.patch  # severity >= patch.auto_fix_min_severity, по умолчанию high
    │       └── all.patch
    ├── index.json
    └── latest -> …
```

## Коды выхода

| Код | Значение |
|---|---|
| 0 | Прогон завершён, critical нет |
| 1 | Прогон завершён, есть critical findings: сигнал, а не ошибка |
| 2 | Внутренняя ошибка (конфиг, git, невалидный вывод модели, hard-timeout) |
| 3 | Другой прогон уже идёт |
| 4 | Ошибка аутентификации или исчерпана квота |

Шаблоны планировщиков передают `--exit-zero-on-findings`, чтобы ночь, в которую честно
нашлись проблемы, не выглядела как упавшая задача.

## Ограничения: прочитайте

- **Закрытый ноутбук на батарее не проснётся.** `launchd` не будит машину; прогон уедет на
  момент следующего пробуждения, то есть слишком поздно, чтобы быть полезным. Инструмент
  регистрирует пробуждение через `pmset` и оборачивает прогон в `caffeinate`, но ни то, ни
  другое не спасёт машину с закрытой крышкой на батарее.
- **Ваш код уходит провайдеру модели.** Проверьте политику работодателя и условия вашего
  плана, прежде чем направлять это на рабочий код.
- **Маскирование секретов снижает риск, но не гарантирует ничего.** Regex-эвристики
  промахиваются на кастомных форматах токенов, а у агента есть собственный доступ к
  файловой системе. Не для кода под регуляторными ограничениями.
- **На `depth: medium` (значение по умолчанию) агент читает файлы за пределами изменений
  ветки.** Scope — изменённые файлы плюс их прямые импорты первого уровня, и до
  импортируемых файлов модель добирается
  собственными `Read`/`Grep`/`Glob`, не через диф. `scope.exclude_paths` маскирует значения
  секретов в дифе, который `review-shift` отправляет — доступ агента к собственному чтению он
  не ограничивает, так что неизменённый импортируемый файл вне досягаемости редактора.
  Находки по-прежнему ограничены изменёнными файлами ветки (импортируемый файл — контекст,
  никогда не цель находки), но само чтение шире. `scope.full_file_review: never` запускает
  промпт и effort `medium` без чтения агентом за пределами дифа; либо опуститесь до `low`.
- **Цифр о качестве пока нет.** Recall и precision заявляются только после появления
  бенчмарк-стенда (v0.2). Что меряет v0.1: применимость патчей.
- **Артефакты прогонов содержат фрагменты кода** и лежат в рабочем дереве.
- **Скоуп v0.1:** только локальные ветки, один репозиторий на прогон. Диффы больше ~2 000
  изменённых строк пропускаются с явной причиной, а не режутся молча. Chunking и retention:
  v0.2; remote-ветки и работа по PR: v0.3. Ревью trunk (`--trunk`) работает покоммитно —
  дефект, размазанный по нескольким мелким и по отдельности невинным коммитам (`wip` → `fix`
  → `actually fix`), всё ещё может проскочить; см. ADR-025.
